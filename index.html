Case Study: Reverse-Engineering Postal 2 into Godot

Tyler | Software Developer | github.com/tboskkk

Summary

In one overnight session, I took Postal 2 (2003, Unreal Engine 2) from an empty folder to a walkable, faithfully lit map running in Godot 4.7. I led the project and made the technical and product decisions; AI coding tools did most of the implementation, inside a review process I set up.

  • Reverse-engineered Unreal Engine 2's undocumented package and level formats; the reader parses all 109 base-game maps byte-exact.
  • Built a full asset pipeline: from game files, through a Python extractor, to a Godot scene, with 539 automated tests.
  • Matched the original look: reused the game's 2003 baked lighting and rebuilt its hidden skybox system, plus an optional modern rendering mode.
  • Personal, private project: it reads the player's own Steam copy and ships none of the game's assets or code.

The problem

Godot cannot open anything Postal 2 ships, and none of the formats are documented. Maps are single packed files (with the extension .fuk) holding thousands of serialized objects: compiled BSP geometry, baked lightmaps, terrain, placed props, lights and gameplay actors.

  • No specification: every structure had to be inferred from the files themselves and validated against them.
  • Engine quirks: Postal 2 uses a licensee variant of Unreal Engine 2 with its own changes to the data layout.
  • Fidelity: the goal was the original look and feel, not an approximation, so lighting, scale and physics had to come from the game's own data.
  • Constraints: a personal learning project that reads the player's own game copy; no game content is committed or distributed.

My role and approach

I acted as the lead engineer: I set scope and direction, made the architecture and trade-off calls, and judged every result. AI coding agents did most of the typing, inside a process I designed so that nothing landed unreviewed.

  1. Spec: agree what to build and why, in a written design, before any code.
  2. Plan: break the spec into small tasks, each with exact interfaces and tests.
  3. Build: one agent implements one task, test-first, and commits it.
  4. Independent review: a separate agent reviews each task against the spec; findings go back for fixes until clean.
  5. Decide: I rule on anything the plan didn't cover, logged with its reasoning and cost if wrong.

The result was fast without being sloppy: 12 milestone tasks, each reviewed, plus a whole-branch review before merging.

Technical highlights

The core of the work was turning undocumented 2003 binary data into a modern engine scene without losing what made it look like Postal 2.

The extractor handles everything unique to the engine; an existing open-source tool covers standard meshes and textures.

  • Binary format reverse-engineering: a Python reader for Unreal Engine 2 packages (names, imports, exports, tagged properties). Each structure was pinned by requiring the parser to consume every object exactly to its stored size, a check that exposes any wrong guess at once.
  • Level geometry: extracted the compiled BSP (12,206 triangles for the first map), terrain heightmaps with layer blending and 49% hole cut-outs, and 1,592 placed props, all converted to Godot's coordinate system.
  • Lighting fidelity: reused the game's own baked lightmaps and per-prop vertex lighting, and recreated per-room ambient light from the map's zone data.
  • The skybox: Postal 2's sky is a small hidden room far outside the map, viewed through a second camera that copies the player's rotation. I rebuilt the same mechanism in Godot.
  • Original physics: the player's height, speed, jump and gravity come from the game's own class data, not guesses.
  • Asset pipeline: integrated an existing open-source extraction tool for meshes and textures, pinned by checksum, behind a validated asset index.
  • Optional enhanced mode: anti-aliasing, ambient occlusion and soft shadows that keep the original brightness and colours, switchable in game.

Results

The first map went from empty folder to walkable in under 3 hours, and to its full original look in about 12.

  • Coverage: all 109 base-game maps parse byte-exact; the first map (Suburbs) is fully playable to walk around.
  • Quality gates: 539 Python tests plus three Godot test suites, all passing; every task independently reviewed.
  • Scale of the first map: 12,206 BSP triangles, 1,592 props, 167 lights, a 256 x 256 terrain and 37 lighting zones.

What's next and what I learned

Next is life in the town: working doors and bystanders, designed as a phased, clean-room reimplementation of the original behaviour on top of an UnrealScript-style state runtime.

  • AI tools multiply an engineer; they don't replace judgement. Most of the value I added was deciding what to build, catching what looked wrong, and saying no.
  • Validate against the data, not assumptions. The strongest checks were the ones the real files could fail: exact byte consumption, every zone actor landing in its own zone, rendered frames compared across versions.
  • Small, reviewed steps beat big ones. Independent review caught real bugs at every stage, from silent data corruption to video timing drift.
  • Respect the source. Reading the player's own copy, shipping no content, and planning clean-room behaviour kept the project on the right side of the original creators' work.
